# WorldForge v0.4.3

Security hardening for the container image and the database engine. Image
availability is confirmed only after the **Release Docker image** workflow
succeeds and the image tag/digest appears in the GitHub release notes.

## Highlights

- Adds verified Docker hardened Debian backports for SQLite
  (`CVE-2026-119373`, `-119374`, `-119379`), ncurses (`CVE-2025-69720`) and zlib
  (`CVE-2026-85091`). CI reads each installed package changelog and applies a
  disposition only when CVE, package and version match exactly.
- Removes setuid from the unused `mount`/`umount` binaries in the runtime image.
- Moves Prisma off its statically linked SQLite 3.46 engine. The application and
  migrations now use Prisma's client engine with `better-sqlite3` built against
  **SQLite 3.54.1**, including FTS5.
- Serializes the synchronous SQLite adapter through a process-wide async lock,
  preserving the existing multi-client transaction tests without blocking the
  event loop.
- Keeps the existing `/data` layout, UID/GID `10001`, origin/proxy requirements
  and operational `pnpm` commands.

## Remaining security findings

This release is **not vulnerability-free**. The image scan still reports **38
high package matches** with no fixed Debian 13 version in the scanner database:

- util-linux: 36 matches across `CVE-2026-76642`, `-78408`, `-78409`, `-78410`
- ACL: `CVE-2026-54369` (1)
- zlib: `CVE-2026-76844` (1)

Runtime mitigations (non-setuid mount helpers, absent `systemd-homed` and Perl
`Archive::Tar`) reduce exposure but do not patch those packages. See
[Container security](https://github.com/emorgan33/worldforge/blob/v0.4.3/docs/container-security.md)
for the evidence, limitations and local scan commands. MySQL/PostgreSQL-style
multi-process concurrency is not provided; SQLite writes still serialize.

## Upgrade

No schema migration is added relative to `v0.4.2`.

**Stop WorldForge and take a verified backup of both the SQLite database and the
full asset directory before upgrading.** Keep the same Compose project name,
`worldforge-data` volume, UID/GID `10001`, origin and proxy network settings.

For a published-image installation, set
`WORLDFORGE_IMAGE=emorgan33/worldforge:0.4.3` in `.env`, then run:

```bash
docker compose pull
docker compose up -d --wait
docker compose logs worldforge
```

For a source-build installation:

```bash
git fetch --tags
git checkout v0.4.3
docker compose up -d --build
```

Native source deployments that want the patched SQLite engine must run
`pnpm sqlite:build` after installing dependencies; ordinary `pnpm install`
leaves the driver's bundled SQLite in place. The supported Docker image always
builds SQLite 3.54.1.

Existing native millisecond timestamps remain readable; no data rewrite is
required. Verify login, representative worlds/articles/search/images, a normal
write, and backup tooling after upgrading.

Rollback requires the older image/source **and** the matching pre-upgrade
database-and-assets backup. Do not run an older application against a database
that has received newer migrations, and do not use `down --volumes` on real data.
