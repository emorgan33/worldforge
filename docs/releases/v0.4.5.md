# WorldForge v0.4.5

First release prepared for **native `linux/amd64` and `linux/arm64`** Docker
images under the same version and SHA tags. Image availability is confirmed only
after the **Release Docker image** workflow succeeds and the platform/digest
details appear in the GitHub release notes. Releases through `v0.4.4` are
AMD64-only.

## Highlights

- Publishes one multi-platform image index with native `linux/amd64` and
  `linux/arm64` children. Docker selects the host platform; pin the recorded
  index digest for a portable reference across architectures.
- Builds, scans, and smoke-tests each platform natively before publication,
  with architecture-scoped vendor evidence and vulnerability reports.
- Validates the complete release index and source-revision labels before reusing
  a version, then publishes only reviewed child content. Version and full-SHA
  tags point to the same validated index; existing same-content tags are no-ops
  and conflicting tags fail closed.
- Re-verifies the published children on both platforms before finalization.
  Release notes update idempotently; `latest` advances only for GitHub's current
  stable release with a stable version tag.
- Adds Oracle Cloud Ampere (ARM64) installation guidance, including native
  platform checks, private app-port/proxy configuration, persistent storage,
  and off-instance database-and-assets backups.
- No application data-model, API, or schema changes are included relative to
  `v0.4.4`.

## Security notes

This release is **not vulnerability-free**. Fixable HIGH/CRITICAL findings block
publication; unfixed findings remain visible in the retained reports. Local
candidate scans currently report 37 unresolved HIGH package matches (util-linux,
ACL, and zlib) plus 12 architecture-scoped vendor-resolved matches. The release
workflow report for this exact tag is authoritative if counts differ.

Evidence is verified separately for `linux/amd64` and `linux/arm64`; a matching
package version does not reuse another architecture's reviewed disposition. See
[Container security](https://github.com/emorgan33/worldforge/blob/v0.4.5/docs/container-security.md)
for policy, limitations, and local commands.

## Upgrade

No schema migration is added relative to `v0.4.4`.

**Stop WorldForge and take a verified backup of both the SQLite database and the
full asset directory before upgrading.** Keep the same Compose project name,
`worldforge-data` volume, UID/GID `10001`, origin, and proxy settings.

For a published-image installation, set
`WORLDFORGE_IMAGE=emorgan33/worldforge:0.4.5` in `.env`, then run:

```bash
docker compose pull
docker compose up -d --wait
docker compose logs worldforge
```

For an ARM64 host such as Oracle Ampere, confirm the pulled image runs natively:

```bash
docker compose exec worldforge node -p process.arch   # arm64
```

Do not add a `platform:` override or use an emulated AMD64 image. Follow the
[Oracle Ampere deployment section](https://github.com/emorgan33/worldforge/blob/v0.4.5/docs/deployment-configuration.md#oracle-cloud-ampere-deployment-arm64)
for firewall, HTTPS proxy, origin, and backup requirements.

For a source-build installation:

```bash
git fetch --tags
git checkout v0.4.5
docker compose up -d --build
```

Native source deployments that want the patched SQLite engine must run
`pnpm sqlite:build` after installing dependencies; ordinary `pnpm install`
leaves the driver's bundled SQLite in place. The supported Docker image always
builds SQLite 3.54.1.

Verify login, representative worlds/articles/search/images, a normal write,
architecture selection, and backup tooling after upgrading. Rollback requires
the older image/source **and** the matching pre-upgrade database-and-assets
backup. Do not run an older application against a database that has received
newer migrations, and do not use `down --volumes` on real data.
