# Autosave and draft recovery

The article editor saves 1.5 seconds after editing pauses, without leaving the editor. New articles start in Draft state and reuse the ID returned by their first save. Save Article remains available to save immediately and return to the article preview.

Only one save runs at a time. Changes made during a request remain dirty and trigger another save afterward. Every first-party edit carries the article version that was loaded or returned by its prior save. The server checks that version as part of the database update, creates the revision and updates mention links in the same transaction, then returns the new version. Changes made during the request therefore use the committed version on their next save. Failed saves show an error and an explicit Retry save action; they do not continually retry. A committed write is still treated as successful if the subsequent list/detail refresh fails.

Local recovery snapshots include fields, rules-profile metadata, canon state, HTML, structured block JSON and the expected article version. They are scoped by account, world, article (or the world's new-article session), and top-level browser window in localStorage. Each window keeps its identity in `window.name`, which survives reloads and is generated independently for a newly opened window even when `sessionStorage` was copied. The editor migrates valid drafts from both previous account-scoped and older world-only keys into its window key. Returning to an editor with a different local snapshot offers Restore draft and Discard draft. Recovery never writes to the server until explicitly restored. Successful saves remove only that window's matching snapshot; newer changes and other windows' drafts stay recoverable. Storage failures are visible. Drafts stay in this browser; clearing browser data removes them. Simultaneous edits in multiple windows are not merged: the first save succeeds, while the stale editor keeps its local draft and receives a conflict with an option to save its work as a separate article. Older local drafts without a version cannot update an existing article; they can be saved as a new article.

Navigation remains blocked during saves. Leaving with pending changes asks for confirmation and retains the recovery snapshot when storage is available. Blank-title drafts are kept locally but are not sent to the server.

Validation: draft parsing tests cover structured content, article identity and rejection of malformed/cross-world data. Chromium checks cover debounced database persistence, editing during an in-flight request, save failure, reload/restore/retry, local snapshot cleanup, and multiple autosaves plus manual completion of a new article without duplication. R06 adds two-editor conflict, stale/versionless recovery, and consecutive autosave version checks. Existing block, organization and RPG tests remain in the suite.

Production verification completed: all 17 automated tests (including the API integration test), TypeScript, focused ESLint and the production build passed. The Chromium autosave/recovery scenarios also passed against the production server on port 3033, with isolated records removed afterward.
