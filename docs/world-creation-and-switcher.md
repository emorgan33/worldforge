# New World and World Switcher

Status: implemented. This document retains the original plan and acceptance criteria; the implementation notes at the end describe the shipped behavior and remaining optional work.

## Outcome and scope

An author can create a private, empty world, open it immediately, and switch between their existing worlds without mixing campaign data or losing unacknowledged edits. This uses the existing `World` model and access rules.

Initial scope is owned author worlds. Player/member campaign selection, world deletion, duplication, starter content generation, importing a whole world, and publishing remain separate features. Creating a world never publishes it, imports Foundry content, or changes another world's rules profile.

## User experience

- Replace the sidebar's display-only world identity with an accessible **World switcher** button. Its popover lists owned world titles and rules profiles, marks the current world, offers search when useful, and ends with **New world**. Duplicate titles remain distinct entries, with a short slug as a disambiguator. Keep the existing article-create button separately labeled **New article**.
- **New world** opens a modal with required title (1–200 characters), existing rules-system choices, and optional description (up to 10,000 characters). Use existing labels: Pathfinder 2e Remaster and D&D 5e 2014; preserve the other supported profiles. Default to the current world's profile, or the existing DND_5E default for a first world. State that new worlds start private and empty.
- Submission says **Create world** and disables repeated submission while pending. Cancel before submission creates nothing. While the POST is in flight, disable Close/Escape and world switching; aborting a browser request cannot undo server creation. Validation and network errors retain the form. If the outcome is ambiguous, allow closing while preserving its pending request for reconciliation. If creation succeeds but opening fails, show **World created; retry opening** rather than invite another creation.
- Success adds the returned world to the switcher and opens its empty campaign home. First-time authors with no worlds see a clear **Create your first world** screen with the same form and sign-out access.
- Switching prompts for unsaved edits where necessary and blocks while a write is pending. Canceling a discard prompt leaves the current world and form intact. Apply the same guard before submitting **Create world** when success would open the new world; declining must create nothing and retain the new-world form. A failed destination load must not consume the discard confirmation by clearing the original form's dirty state. The picker also remains available when loading a destination fails.
- Modal and popover support keyboard navigation, visible focus, Escape, appropriate labels, focus return, and readable dark-theme text. Render the modal outside settings forms and stop submit propagation through React portals.

## Existing foundations and required corrections

- `src/app/api/worlds/route.ts` has owner-filtered GET and a PATCH handler currently blocked by its path-based authorization wrapper, but no POST. GET currently orders by update time, which must stop determining the active world.
- `src/lib/auth.ts` authorizes world writes from the path ID. Collection POST has no existing world ID, and collection PATCH supplies its ID in JSON. Give these two exact routes explicit handling: POST requires a signed-in actor and same-origin request; PATCH requires ownership of its validated body ID. Do not weaken authorization for nested world routes or resource writes. Add regression coverage for both PATCH call sites: world settings and campaign rules selection.
- `AuthorWorkspace.tsx` currently loads the first world and then sequentially fills independent state arrays. Extract loading and selection before adding switcher interactions; do not duplicate that effect for each selection.
- `WorldHome`, compendium forms, variable edits, map pin creation, session forms and Foundry imports hold state beyond the existing article `editorDirty` flag. The guard inventory must also cover AssetLibrary uploads/metadata edits, image pickers, category mutations and secret editors. Inventory these writable surfaces and include them in the switching boundary. Resetting only article state is insufficient.

## Creation contract and data

`POST /api/worlds`

```json
{
  "title": "The Ashen Coast",
  "description": "An optional setting introduction.",
  "system": "PF_2E",
  "requestId": "a UUID retained across retries of this submission"
}
```

1. Require session authentication and same-origin protection before parsing a bounded JSON body (64 KiB). Validate object shape, title, description, system against existing constants, and request UUID. Normalize whitespace consistently; reject unsupported fields rather than mass-assign them.
2. Derive `ownerId` from the session. Generate world ID and unique slug on the server; never accept client ownership, public visibility, images, categories or arbitrary mapped model fields. Use the existing private/default model settings and create no starter records or image assets.
3. Generate a readable title slug with a random suffix, including a fallback for titles without ASCII letters. Handle actual unique-constraint collisions with bounded retries; a preflight uniqueness check alone is insufficient. Same-title worlds are allowed.
4. Add nullable `World.creationRequestId` and `World.creationPayloadHash`, with a composite unique index on `(ownerId, creationRequestId)`. Existing worlds keep null values. Store a hash of the normalized creation payload. The first request returns 201; a same-owner/same-key/same-payload retry returns the existing world with 200. A reused key with different content returns 409. Concurrent submissions converge through the unique constraint. Never deduplicate by title or overwrite an existing world.
5. Before POST, retain the normalized payload, request UUID and pending state in component state and account-scoped session storage. Restore pending requests on dialog reopening/reload; after an ambiguous failure retry that exact payload/key, not a fresh creation. If the user changes that payload, make starting a distinct submission explicit and first offer reconciliation with the original request. An intentional later creation gets a new key. Persist a confirmed world ID when opening fails, and retry opening that ID without POSTing again. Clear recovery only after resolution. When browser storage is unavailable, creation can still work with in-memory retries; explicitly limit recovery to the current page lifetime, never automatically submit a replacement after reload, and offer the authorized world list for checking an uncertain outcome. Do not promise that closing or reloading cancels server creation.
6. Return an explicit response projection compatible with the existing `WorldSummary`/GET shape, including empty categories and counts where expected; exclude internal creation keys/hashes. Apply the same explicit projection to **GET and PATCH**, which currently return all World scalar fields. Backup/restore retains ordinary world data but not creation request metadata; restored worlds receive fresh identity. Verify public projections stay explicit as well.

The migration is additive. Verify nullable unique behavior on SQLite, fresh migration application, upgrade of a populated database, existing backup/restore behavior, and no loss of existing worlds. Back up the local database before applying it. No changes to Foundry provenance or ownership rules are needed.

## Selection, loading and navigation

- Use `/?world=<worldId>` as the canonical author-workspace selection. It survives refresh and supports browser Back/Forward; public `/w/<slug>` URLs remain reader pages. Preserve unrelated query parameters.
- With no world query, restore an account-scoped last-used ID from browser storage only if it is present in the current authorized world list. Otherwise choose a deterministic existing world, or the first-world screen. Write the resolved selection into the URL using replace, avoiding an extra history entry. Storage failure must not prevent opening a world.
- Pass only the authenticated `user.id` from `src/app/page.tsx` to the client workspace for storage scoping; the current component receives no actor ID. Resolve account identity before reading account-scoped state, and clear in-memory account state on sign-out/account change.
- An explicit malformed, deleted or inaccessible query ID shows **World unavailable** and an authorized chooser; never silently replace it with another campaign or reveal another author's world title. URL/storage identifiers are hints, never authorization.
- Extract a small world loader that uses the existing world-scoped APIs. Fetch independent datasets concurrently and check every response. Include articles, categories/world summary, variables, maps, timelines, secrets, RPG blocks and sessions. A required-dataset failure shows a retryable load error, not an apparently empty campaign. Distinguish 401 from unavailable-world and ordinary network failures.
- Use an AbortController plus a monotonically increasing selection token. Only the latest requested world may commit a complete snapshot. Abort alone does not protect responses already parsed. Never display A's records under B's title while switching; loading/error views must hide inactive data.
- Keep the previous complete snapshot **and its keyed component subtree mounted** until the transition succeeds. Hide/inert that subtree beneath the loading/error boundary rather than unmounting its unsaved forms. Freeze interactions and pause scheduled autosaves/new writes during the transition; resume them when returning after failure. Dirty flags and discard/reset occur only when a successful destination snapshot commits. Include an explicit return-to-current-world action on failure. Commit world identity and its records together. Push URL/history only for a confirmed user switch; Back/Forward selection follows the same guard and loader, restoring the current URL if leaving is declined. Do not create navigation loops or leave URL and visible world inconsistent.
- Specify and test history traversal in milestone 2 before wiring the picker: track application-created history-entry indices while preserving Next's existing history state. A declined Back/Forward or failed traversal compensates to the original index; do not replace the traversed entry with the previous URL and destroy the destination. Suppress only the compensating event, serialize rapid traversal requests, and test repeated Back/Forward after cancellation. Retain the existing native before-unload protection for navigation outside the managed workspace history. Verify these mechanics against the installed Next.js navigation guide rather than assuming router interception APIs.
- Reset active view to campaign home, selected/current article, category/editor defaults, compendium filters/focus, searches and pending dialogs on successful switch. Key the world workspace subtree by world ID to reset child-local state. Retain only valid account-level state.
- Capture the destination world ID for writes. Block switching while writes are in flight, including autosave, settings saves and an in-flight Foundry batch. Guard late callbacks and background refreshes by world ID/selection token so they cannot update a different world's state. Foundry cancellation stops future batches and waits for the current batch before a switch.
- Extend a small shared navigation-guard interface for dirty/busy child forms rather than introducing a new application-wide state framework. Register/unregister per mounted form. Reuse existing article recovery and confirm behavior; never delete recovery drafts on switch. Existing article draft keys are world-only (`worldforge:draft:<worldId>:<articleId-or-new>`). Move to account+world-scoped keys with a compatibility reader: only inspect a legacy draft for an authorized selected world, validate it with the existing parser, copy it safely to the new key, and retain the legacy entry until recovery/save or explicit discard resolves it. Storage errors must not strand existing recovery. Audit other storage keys and article references for both account and world scope.
- Keep the owned-world list in sync after creation and settings changes. Refresh on picker open when necessary and validate the requested selection against the refreshed authorized list. A selected world's own load can still fail after that check; handle it safely.

## Acceptance criteria

### World lifecycle API

`DELETE /api/worlds/{id}` archives an active world. It sets `deletedAt`, keeps the title and other world settings intact, and makes the world private. `GET /api/worlds/deleted` lists the signed-in owner's archived worlds. `POST /api/worlds/{id}/restore` restores an archived world as private. Permanent deletion is available only for archived worlds through `POST /api/worlds/{id}/purge` or `DELETE /api/worlds/{id}/hard`; related database rows use the schema's cascade rules and asset files are removed through a durable retry queue.

`POST /api/worlds/{id}/duplicate` creates a **settings-only** private world. The request body is `{ "requestId": "<UUID>" }`; the request ID is scoped to the authenticated owner and supports safe retries, including after source settings change. The response is the normal `WorldSummary` projection. It copies the source title with ` (settings copy)` and the rules system, while starting with no content or image references. Reuse of a request ID for a different source or ordinary creation returns `409`.

1. An author with zero worlds can create one, opens its empty home and sees it selected. A returning author can create another without altering their current world's content. Cancel before submission and validation errors create nothing.
2. Created worlds belong to the authenticated author and start private. Client-supplied ownership/public/model fields, unauthenticated requests, cross-origin writes, malformed/oversized input and unsupported profiles fail safely.
3. Same-title worlds remain distinct. Double-clicks, concurrent identical requests and retry after a lost response create exactly one world for the request key. Different payload under that key returns conflict without overwriting. Dialog reopening/reload restores pending creation when storage is available; denied storage follows the explicitly limited recovery behavior without automatic resubmission. Closing an ambiguous request never claims to cancel it.
4. The switcher lists only owned worlds, identifies the selected one and supports keyboard/search/duplicate-title disambiguation. Profile labels distinguish D&D 2014 and PF2e Remaster.
5. Switching A → B loads only B's complete data. Reversed network response order, canceled loads, late article-detail responses and stale mutation callbacks cannot mix A's records into B. Test every world dataset, not just title/articles.
6. Reload retains selection; explicit URLs and Back/Forward work, including canceled Back followed by Forward/repeated Back, rapid traversals and failed target loads without lost history entries. Missing/deleted/foreign IDs show an unavailable state with no data disclosure. Last-used browser storage from another account cannot select or expose a foreign world; blocked storage is harmless.
7. Dirty article/settings/compendium/variable/map/session/asset/secret forms either retain edits when switching is declined or discard only after explicit confirmation and successful transition. Failed loading retains the original mounted forms and their dirty flags. Legacy article recovery remains usable after account scoping. Switching is blocked during saves, uploads, category writes or a Foundry batch; no write is redirected into the newly selected world.
8. Load/creation errors are visible and recoverable. A world created successfully but failing to load is offered for reopening, not created again. An unsuccessful switch does not leave mixed content or an inconsistent URL.
9. Existing world settings, rules-profile updates, article creation, Foundry import, publication and backup/restore continue to work with the selected world. Internal creation metadata is absent from public output and backup copies.
10. Run meaningful creation/API/race/guard tests against isolated databases, then the project test suite, TypeScript, changed-file ESLint and production build. Report server-dependent skips explicitly. Use a production browser session for first-world creation, two-world switching, refresh/history, denied discard, network failure/retry, keyboard access and the Foundry import regression. Remove temporary test records; keep user data intact.
